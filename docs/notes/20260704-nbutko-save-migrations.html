Save migrations are brittle by design

The save version is a hard-coded exact match; anything migrate() doesn't recognize as v2, v3, or v4 falls back to a brand-new save with no error.

author: nbutko · opened: 2026-07-04
When to read this. You're adding, removing, or renaming a field on SaveData (src/domain/save.ts), or debugging why an old save silently reset to fresh/character-creation instead of loading. The version check is exact-match, not "close enough" — a shape that almost matches still falls through to defaultSave().

Relevant when

You're touching src/domain/save.ts's shape or version, or a save appears to have reset for no visible reason.

The gotcha

As of today SaveData.version is 4 (not 3 — that was true through M3/early M4 but a real migration bumped it again in M5). isSaveData() requires raw.version === 4 exactly, and migrate() tries v4, then v3, then v2 shapes in turn; anything that matches none of the three (missing, corrupt, or older than v2) falls back to defaultSave() — a fresh save, no error, no warning. Two real migrations exist:

  • v2 → v4 (migrateV2): keeps coins, highestUnlockedTier, monstersDefeated, and stats; drops the retired skillTree; sets character: null so the player is routed through character creation once (there's no v2 character to reconcile, so it jumps straight to v4 instead of stopping at v3). See the M3 PRD's "What this changes" section for why wiping to a fresh character was judged acceptable for a solo project.
  • v3 → v4 (migrateV3, added by ad47bb7): through v3 the live XP path (award) bumped xp but never re-derived level or banked ASI points, so every v3 character was frozen at level 1 no matter how much XP it held. This migration re-derives the real level from the XP total and backfills the ASI points earned along the way — a one-time backfill that the version bump ensures runs exactly once (re-running it would double-bank). See the M5 plan's 2026-09-12 reconciliation callout for why this predates the plan and isn't credited to any of its stories.

Even an already-current v4 save gets reconcileLevel re-applied on every load (idempotent) — cheap insurance so level can't drift from XP if a future XP-curve retune shifts the thresholds.

What to do

When the SaveData shape changes again: bump version, add a new isVN / migrateVN pair mirroring the existing ones in src/domain/save.ts, and write a real migration function — don't just widen isSaveData's check, or every existing save silently resets instead of migrating. Read src/domain/save.ts directly before trusting any doc's stated version number, including this one; it's the one place this is guaranteed current.
