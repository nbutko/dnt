No backend/server for v1. Everything is a static site. This eliminates an entire category of work (auth, database, hosting a server, cost) for a project with exactly one player.

State: no Redux, but three distinct homes

"State in React components" is right for the save file and the menus, but a battle is a real-time simulation, not a form — the monster's live typing, both HP bars, and both countdowns update many times a second. Pushing that through scattered useState/useEffect tangles the combat math with rendering and makes "do the numbers feel right?" impossible to test in isolation. The fix is not a state library; it's putting each kind of state where it belongs:

KindExampleHome
Simulation / battlemonster's typed string, HP bars, countdownsA framework-agnostic engine (a factory function per no-class) that owns the state and advances via tick(dt); React reads it through useSyncExternalStore
Persistent / savecoins, the character (class/level/XP/abilities), equipped weapon + inventoryReact Context + useReducer — cross-component and low-frequency, the textbook Context case (arrives in M2)
Ephemeral UIthe player's typed line, which screen is upLocal useState — the typed line lives in ui/hooks/useTypingInput.ts, built from window keydown (there is no text field)
Redux/Zustand really would be overhead — but the reason isn't "the app is small," it's that none of these three problems is the one Redux solves. Context re-renders every consumer on every change (fine for a save file that changes once a battle, pathological for state ticking 60×/sec), which is exactly why the battle lives in an external-store engine instead. Keeping that engine free of React imports is also what lets M0 test the combat math headlessly and run a balance simulator over it. See the M0 implementation plan for the file layout that draws this boundary.

FormatterPrettier, printWidth: 100, semi: false, tabWidth: 2, useTabs: false; eslint-config-prettier turns off any ESLint stylistic rule that would fight it
Prettier is what makes semicolon-free code actually safe, not just shorter. The classic ASI footgun is a line starting with (, [, a backtick, +, or - silently merging with the line above and changing meaning. Prettier detects exactly this and inserts a disambiguating leading ; automatically — so ASI safety comes from letting the formatter run, not from writing careful code by hand.

Two custom syntax bans

Enforced via ESLint's no-restricted-syntax (no extra plugin needed — it targets AST node types directly):

  • no-function — ban FunctionDeclaration and FunctionExpression; arrow functions only. Object method shorthand ({ attack() {...} }) doesn't use the literal function keyword, so it's unaffected and stays the idiomatic way to put a method on a plain object. One consequence: arrow-function consts don't hoist the way function declarations do, so mutually recursive helpers need to be ordered top-down. Arrow functions also can't be function* generators or used with new — not expected to matter here, but if the monster-typing character stream (Monster typing) ever wants a generator, that's a spot to revisit.
  • no-class — ban ClassDeclaration and ClassExpression; use factory functions (a function returning a plain object, closing over any private state) instead of instantiated classes. This only bans authoring classes in our own code — using a class from a library (e.g. whatever idb hands back, new Map(), new Error()) is unaffected, and an Error subclass becomes Object.assign(new Error(message), { code }). Costs nothing on the React side, since the project was always function components + hooks; eslint-plugin-react-hooks (rules-of-hooks, exhaustive-deps) is in the baseline alongside it.

import/extensions is off and import/resolver is set to typescript so Airbnb's Node/webpack-tuned import rules don't misfire on Vite + TS path resolution. no-console is warn-only rather than Airbnb's default off, so a solo side project can leave breadcrumbs in without doing so silently. Linting isn't wired into a pre-commit hook or the GitHub Actions build — npm run lint + tsc (npm run build) + npm run test (npm run presubmit) are run by hand before every commit, per CLAUDE.md's working rules.

Save data & persistence

One JSON-shaped record, versioned so future shape changes can migrate it:

{
  "version": 4,
  "character": {
    "name": "Aria",
    "class": "fighter",
    "level": 3,
    "xp": 900,
    "abilities": { "str": 15, "dex": 12, "con": 14, "int": 10, "wis": 10, "cha": 8 },
    "pendingAsi": 0
  },
  "coins": 120,
  "equippedWeapon": "longsword",
  "inventory": {
    "weapons": ["dagger", "longsword"],
    "consumables": { "potion-healing": 2, "luckstone": 1, "...": 0 }
  },
  "hearts": { "max": 2 },
  "highestUnlockedTier": 3,
  "monstersDefeated": ["slime", "goblin"],
  "stats": { "battlesWon": 7, "battlesLost": 2, "bestWpm": 28 }
}
character replaced the M2 skillTree/xp fields in M3 (see the M3 scope doc) — null is the "uncreated" marker that routes a fresh or freshly-migrated save through character creation before the world map. equippedWeapon and inventory are new alongside it; XP now lives on the character and crosses level thresholds automatically instead of being a spendable currency. hearts/highestUnlockedTier (added in M2, see the M2 scope doc) carry over unchanged. Deliberately still not in this record: the in-progress dungeon graph, cleared nodes, hearts remaining mid-run, or any active consumable buff — that state is meant to be thrown away on death/leave/re-visit by design, so persisting it would fight the game's own rules rather than support them. The record is now version 4: a one-time backfill re-derives character.level and pendingAsi from XP for any save whose level had been frozen at 1 by an earlier leveling bug, and the same re-derivation runs (harmlessly, idempotently) on every load so a level can never drift from its XP again — e.g. after an XP-curve retune shifts the thresholds.

Stored in IndexedDB rather than localStorage — via a thin wrapper like idb so the app code never touches IndexedDB's raw callback API directly. Access goes through a small interface, not scattered get/set calls: 

interface SaveStore {
  load(): Promise<SaveData | undefined>;
  save(data: SaveData): Promise<void>;
}
IndexedDB over localStorage, specifically for the migration path: its API is already async and works with structured objects, which is exactly the shape a future network call (fetch to a real backend) would have too. If a cloud DB is ever wanted — cross-device sync, a second kid's profile, anything — swapping the SaveStore implementation from an IndexedDB version to a networked one is a localized change behind that one interface, with no rewrite of call sites. localStorage's synchronous get/set API doesn't have that shape, so every caller would need to change, not just the storage layer.
Still no backend/cloud sync in v1 — this is purely about leaving the door open cheaply, not building it now. See Roadmap: this is a post-V1 concern, not a blocker for any milestone.

Data model for content

Monsters and text banks are plain data files (JSON or .ts const exports), not hardcoded in components — see Content Plan. This keeps "add a monster" or "add ten lines to tier 3" a content edit, not a code change.

Getting it onto the Chromebook

The game is live at nbutko.github.io/dnt, hosted as a static site on GitHub Pages. A GitHub Actions workflow (.github/workflows/deploy.yml) runs npm ci && npm run build on every push to main and publishes dist/ to Pages — no separate deploy step, no server to maintain, updates go live the instant a push lands. vite.config.ts sets the build's base to /dnt/ (Pages' project-page subpath); npm run dev always serves from root, so an absolute asset path that works locally can 404 once deployed — reference assets through Vite's own resolution (an import, or %BASE_URL% in index.html), never a literal leading /.

It installs as a PWA: "Install app" / "Add to Home screen" from Chrome's menu pins a real icon to the shelf and opens the game full-screen. The manifest and service worker (public/manifest.webmanifest, public/sw.js) are hand-written rather than generated by vite-plugin-pwa/workbox, specifically so the PWA can't break under Vite's Rust-based (rolldown-vite) bundler. The worker caches on demand rather than precaching a build manifest: navigations are network-first (so a fresh deploy is picked up while online, falling back to cache offline), everything else — hashed JS/CSS, the favicon, Google Fonts — is cache-first. Fonts still load from the Google Fonts CDN at runtime; the worker just caches them after first use, so offline works once there's been one online visit. sw.js runs outside the typed app graph and is excluded from ESLint accordingly.

The game is a public static SPA with no backend — the save lives in the browser's own IndexedDB, so progress is per-device by design (no cross-device sync, no accounts). The URL is public on the open internet: not listed anywhere or discoverable without the link, but not access-controlled either, which is fine for a game with no personal data beyond a local save file.

GitHub Pages was the pick because a GitHub account already existed — no new sign-up, and it's free. It costs one extra piece Vercel/Netlify don't need: the small GitHub Actions build-and-publish workflow above. Nothing about the app itself is host-specific, so switching to Vercel, Netlify, or Cloudflare Pages later (any of which would also support a real custom domain, e.g. dungeonsandtyping.com, with a few minutes of DNS setup) stays cheap if the Actions step ever becomes annoying.

Non-goals

  • Multiplayer / PvP
  • Accounts, login, or cloud sync — deliberately left possible via the IndexedDB SaveStore interface above, but not built
  • Mobile app store packaging (the PWA covers "icon on the device")
  • Monetization of any kind
