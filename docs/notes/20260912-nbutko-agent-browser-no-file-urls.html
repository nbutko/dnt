Agent browser tools can't open file:// URLs — and the dev server can't tell you a link is broken

A human opens docs straight from disk; an agent's browser tool needs npm run dev and /docs/... — and either way, the dev server's SPA fallback returns 200 for any path, so HTTP link-checking is meaningless here.

author: nbutko · opened: 2026-09-12
When to read this. You're an agent about to verify a doc renders correctly, or about to write a link-checking script, or wondering why a browser tool navigation to a local file path fails outright.

Relevant when

You're rendering-checking a docs/ page with a browser tool, or writing/running any kind of link audit.

The gotcha

A human maintainer can open any docs/ page directly with a file:///Users/.../dnt/docs/... URL — every doc's relative stylesheet and links are written to work that way. Agent browser tools, however, are blocked from opening file:// URLs at all, so an agent must instead run npm run dev and open http://127.0.0.1:5173/docs/... (the dev server serves the whole repo root, not just the app). Separately — and this trips people up even when using the dev server — Vite's SPA fallback returns HTTP 200 for any path that doesn't match a real file, because it's designed to hand unmatched routes to the client-side app. That means an HTTP-based link checker (curl, fetch-and-check-status) cannot distinguish a real doc page from a typo'd path: both return 200. It looks like proof a link works when it proves nothing.

What to do

Verify docs render by opening them with an agent browser tool via npm run dev's 127.0.0.1:5173/docs/... URL, not file://. Check links by reading the filesystem directly (does the target path actually exist on disk), never by an HTTP status code against the dev server — see the docs-refactor plan's §7.1 link audit for the filesystem-based script this project actually uses.
