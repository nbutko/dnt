stats.battlesLost is a dead field

It exists in the save shape and in tests, but no reducer action anywhere ever writes it, and nothing reads it — it's permanently 0 on every real save.

author: nbutko · opened: 2026-09-12
When to read this. You're building a feature that would want a loss count (a hall-of-records screen, a win/loss ratio stat, a "close call" achievement) and are tempted to read save.stats.battlesLost expecting it to hold real data.

Relevant when

You're about to read or display stats.battlesLost, or wondering why it's always 0.

The gotcha

SaveData.stats (src/domain/save.ts) declares { battlesWon, battlesLost, bestWpm }, and battlesLost defaults to 0 like the rest. But state/save/save-reducer.ts's award action — the only place stats is ever updated — increments battlesWon on every win and never touches battlesLost anywhere (confirmed: it's the only stats. write in the reducer). No action fires on a loss to increment it either. Nothing in src/ui/ reads the field. Unlike stats.bestWpm and powerUpMultiplier, which were "lit up" (wired to real writers) in M3, battlesLost never got its writer.

What to do

Don't build a feature on the assumption this field already tracks losses — it doesn't, on any existing save. To make it real: add an action (or extend an existing one, e.g. wherever a dungeon-run wipe is recorded) that increments stats.battlesLost on a lost battle, the same way award increments battlesWon today. No save migration is needed since the field and its default already exist in the v4 shape — only a writer is missing.
