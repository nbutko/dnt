Plan: Typing Input Rework

Replace the battle screen's hidden <input> with a window keydown listener, so typing needs no DOM focus and there is no text field for ChromeOS to autocorrect.

Closed 2026-09-13.

This is the implementation plan for typing-input-rework. It fixes two bugs reported from the Chromebook against the core battle screen: (1) typing goes dead mid-fight and never comes back until a page reload, and (2) typed words are sometimes autocorrected, which turns a correctly-typed line into a miss. Both are consequences of one design choice in src/ui/battle/PlayerPrompt.tsx, so this plan replaces the mechanism rather than patching each symptom. Conventions used throughout (naming, lifecycle, banners, checkboxes) are in conventions.html.

Diagnosis. The battle reads keystrokes through a real <input> that is visually hidden (sr-only) and treats its .value as the typed string. That element must hold DOM focus to receive anything, and it only ever gets focus from autoFocus on mount (and on remount after a miss pause, since the paused branch unmounts it). Any touchpad tap, touchscreen tap, or Tab press moves focus off it, nothing ever moves focus back, and because the element is invisible there is no box to click into — hence "never regained until page load." Separately, ChromeOS applies its own auto-correction, auto-capitalization, and spellcheck to any editable text field, and this is a bare text field with none of the opt-out attributes; ChromeOS's physical-keyboard autocorrect has historically not honored those attributes reliably anyway. Remove the text field and both bugs become structurally impossible.

1. Scope

  • In: how the player's in-progress input string is built during a battle (ui/battle/BattleScreen.tsx, ui/battle/PlayerPrompt.tsx, a new hook under ui/hooks/); the tests that exercise it; every comment and evergreen doc that describes the hidden input; a note recording the gotcha.
  • Out: the combat engine, the battle store, the Keyboard/TypedProgress rendering, the submit rule (Enter only counts once lengths match; exact match hits), and the M5 plan's unrelated dt-clamp fix (B3) — see §6.
  • Deliverable: mid-fight, clicking or tapping anything on the page and then typing still lands keystrokes in the prompt; on the Chromebook, a correctly-typed line is never rewritten by the OS.

2. Approach

Two stories, code first then docs, per the working rules. The code story moves keystroke capture out of the DOM and into a window keydown listener that is only armed while the battle is ongoing and the player is not paused. BattleScreen already owns the input state (lifted there in M0 Story 7 because the Keyboard needs it too), so the listener lives beside it as a small hook and PlayerPrompt becomes purely presentational. The codebase already uses exactly this idiom for Enter in ui/dungeon/EncounterModal.tsx, so nothing new is being invented.

No text field, anywhere on the battle screen. The typed string is built from KeyboardEvent.key and nothing else. Do not reintroduce an <input>, <textarea>, or contentEditable "for focus" or "for accessibility" — that is the thing that broke.

3. Decisions

Keydown listener over a refocus band-aid. The M5 plan's Story 1 proposed keeping the hidden input and re-focusing it on mousedown/blur. That fixes only the focus half, fights every future modal or autofocused button, and leaves the autocorrect half to opt-out attributes that are unverified on the one device that matters. A listener needs no focus and gives the OS no field to rewrite. Its cost is one hook of roughly thirty lines. The B2 half of M5 Story 1 is superseded by this plan; its B3 half (clamp the game loop's dt) stays there.
The hook is the one keystroke authority; it lives in ui/hooks/useTypingInput.ts. Signature: useTypingInput({ prompt, attempt, active, onSubmit }) → input. It owns the input state (moving it out of BattleScreen's useState), resets to '' whenever attempt changes (today's useEffect), and subscribes to window keydown only while active. Mirrors useGameLoop: a headless, testable seam between the DOM and the battle. BattleScreen passes active = state.status === 'ongoing' && !state.player.paused.
Key handling rules. In order, per keydown:
  1. Any of ctrlKey, metaKey, altKey held → ignore (browser and ChromeOS shortcuts keep working; Shift is not a modifier here, it is how capitals are typed).
  2. key === 'Enter' → if input.length === prompt.length, preventDefault and onSubmit(input); otherwise ignore. Same rule as today's handler.
  3. key === 'Backspace' → preventDefault, drop the last character. Backspace is always allowed (game-design.html, "Submitting an attack").
  4. key.length === 1 → preventDefault (so Space cannot scroll the page), append. This is every printable character a physical keyboard produces, including capitals and punctuation via Shift.
  5. Anything else (Shift, Tab, arrows, Dead, function keys) → ignore.
event.repeat is honored, not filtered: holding a key auto-repeats exactly as a text field would, and a kid who leans on a key gets an off-track line and a Backspace highlight, same as today.
Gating replaces focus management. On a win the reward modal mounts over the still-mounted battle screen (ui/dungeon/DungeonScreen.tsx), but status is already 'won' so the listener is off and Enter reaches only the modal's autofocused Continue. On a loss status is 'lost', so the in-battle Continue button's autofocus works unchanged. During a miss pause the listener is off, so keystrokes typed at the "You missed!" message are dropped instead of silently pre-filling the next prompt — the same behavior as today's unmounted input.
Enter-as-literal-character stays dormant. game-design.html says a short-input Enter is treated as a literal character so prompts with inline line breaks type unambiguously. Today's <input> cannot hold a newline, so that rule has never actually run, and every string in src/content/text/library.json is single-line ASCII (checked 2026-09-13: 6,893 strings, zero newlines, zero non-ASCII). The new hook ignores a short-input Enter, exactly as today. If multi-line prompts are ever authored, appending '\n' on a short-input Enter is a one-line change in the hook; it is not done here.
Paste and screen-reader text entry are dropped on purpose. A typing trainer has no use for paste, and the one player does not use a screen reader. The prompt line and keyboard remain ordinary rendered text.

6. Out of scope, deliberately

  • The game loop's unclamped dt (M5 bug B3). It also reads as "the game broke" on returning to a tab, but it is a different mechanism in a different file; it stays in the M5 plan's Story 1.
  • Tapping the on-screen keyboard to type. The Keyboard component is a display aid; making its keys touch targets is a feature, not a fix, and would need wireframes.
  • IME, dead keys, non-ASCII prompts. No bank text needs them; if a future content tier does, the hook's "ignore anything that isn't a single-character key" rule is where that work starts.
  • Accessible text entry. Deliberately dropped with the input (§3).
