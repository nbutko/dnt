PRD: Docs Refactor

One documentation layout that stays trustworthy as the project keeps growing — evergreen docs that describe now, dated artifacts that record how we got here, and notes that catch the gotchas in between.

feature: docs-refactor · author: nbutko · opened: 2026-09-12 · status: wip

This is the product requirements document for the docs-refactor feature. It is also the first artifact written under the conventions it proposes, so its own location and name (docs/prds/wip/20260912-nbutko-docs-refactor.html) are part of the spec. A companion implementation plan covers how; this document covers what we want and why, not how. The file-by-file inventory of where each existing document lands belongs to the plan.

1. The problem

Almost every "how / why" question about dnt is answered somewhere in docs/ — the project's standing rule is read the docs before spelunking the code. That rule only pays off if a reader can find the right doc and trust what it says. Today neither is reliable:

  • Evergreen and historical docs are interleaved in one flat directory. Sixteen HTML files sit side by side: the always-current codebase map, three generations of the content plan (v1, v2, v2-tuning), four milestone scope/implementation pairs, and an audit. Nothing in the layout says which ones describe the game as it exists.
  • "Current" docs have quietly gone stale. index.html still says "Planning stage — no code yet." The roadmap describes M4 as future work and lists a crit-range gap as "pending" that CLAUDE.md says was closed. CLAUDE.md itself hard-codes "M3 is done; M4 is next" while the repo is mid-M5. Each of these was true when written; none is now, and there is no rule that made anyone responsible for updating them.
  • The same document tries to be two things. The design README.md is both a wireframe handoff (rejected alternates, "which option is canonical") and the as-shipped visual reference. Content Plan v2 is both a requirements doc (the 14-tier ladder) and a build log (measured prototype results). Readers have to mentally separate "the decision" from "the record of making it."
  • Hard-won gotchas live in the wrong places. Save-migration brittleness, the dead stats.battlesLost field, the "post-playtest feedback logs" at the tail of the M2 plan, file:// URLs being blocked in the agent's browser tools — these are scattered across CLAUDE.md, plan appendices, and one agent's private session memory. A new agent hits the same wall twice, and an agent working for a different person never sees the memory at all.
  • There is no convention to follow. Naming is ad hoc (m3-scope, content-plan-v2-tuning-implementation, M0 Wireframes.dc.html), there is no notion of "in progress" versus "finished," and nothing tells the next contributor what to write before starting a feature or what to update after finishing one.
The docs are written and read overwhelmingly by AI agents working in short sessions with no memory of the last one. That makes documentation structure a load-bearing part of the development process here, not a nicety: every session re-orients from scratch, and every stale sentence in an evergreen doc costs a wrong assumption or a code spelunk. The structure has to make "which docs are true right now" answerable from the directory listing alone.

2. Goals and non-goals

Goals

  1. Trust by location. Anything at the top level of docs/ describes the project as it is built today. Anything in a subdirectory is either shared presentation (style/), a dated development artifact (prds/, wireframes/, plans/), or a dated gotcha (notes/).
  2. A repeatable feature lifecycle. Every piece of work — feature, retune, bug batch, refactor — leaves the same trail: an optional PRD, optional wireframes, a required plan, all moving from wip/ to done/ with the evergreen docs updated on the way out.
  3. Cheap orientation for agents. A new session can read CLAUDE.md, the docs index, and the four sub-indexes and know exactly which full documents are worth loading into context.
  4. Reshape the history into worked examples. The existing scope docs, plans, wireframes, and design handoff already contain PRD-shaped rationale, wireframe-shaped screens, and plan-shaped story lists — just not separated. Pulling those portions apart into properly shaped, dated PRD / wireframe / plan documents preserves the record and gives future authors concrete examples of what each type looks like. Where a milestone recorded nothing (M1 has no doc of any kind), the gap stays a gap; we restate and reorganize what was written, we do not invent what wasn't.
  5. Written-down conventions. A future contributor (human or agent) can follow the pattern without having read this PRD, because an evergreen doc explains it, templates exist to copy, and CLAUDE.md points there.

Non-goals

  • Changing game code, tests, or the build. This feature touches docs/, CLAUDE.md, and the handful of source comments that link into docs/.
  • Re-deciding anything. Reshaped historical documents restate the rationale and plans that were actually recorded at the time; they do not second-guess them, and they carry a status banner saying how the work actually ended.
  • Switching document format or adding tooling. Docs stay plain, hand-written HTML sharing one stylesheet, readable by opening the file directly in any browser — no build step, no generator, no link checker in CI. A convention plus a manual link pass at each feature's close is enough for one repo and one kid.

4. What we're building: the target layout

docs/
├── index.html                 ← evergreen: pitch, principles, doc index, links to the four sub-indexes
├── (other evergreen docs)     ← present tense only: architecture, codebase map, game design,
│                                content, visual spec, roadmap ("where we are, what's next"), conventions
├── style/                     ← shared CSS, templates, any visual asset used by more than one doc
├── prds/
│   ├── index.html             ← every PRD, short description each, grouped wip / done
│   ├── wip/                   ← (no index here)
│   └── done/
├── wireframes/  index.html + wip/ + done/     (same shape)
├── plans/       index.html + wip/ + done/     (same shape; a plan is required for every piece of work)
└── notes/
    ├── index.html             ← every note, one sentence each on when it's relevant
    └── YYYYMMDD-author-topic.html

4.1 Evergreen docs (top level)

  • Describe the project as built today, in the present tense. No milestone narration, no "originally," no "was replaced by," no "pending."
  • May — and should — explain why things are the way they are, as long as the reasoning is the current understanding. "The engine never imports React because…" belongs in an evergreen doc. "In M2 we tried a skill tree, then in M3 replaced it…" does not; the evergreen doc states the current design and links to the done/ artifact for the story.
  • Are the only documents with a maintenance obligation: closing any feature includes updating the ones it affected.
  • Include a conventions doc — the rules in this section, the naming pattern, the lifecycle checklist, and where the templates live — so the pattern survives without this PRD.

4.2 Dated artifacts: prds/, wireframes/, plans/

  • Naming: [YYYYMMDD]-[author]-[feature-name].html, e.g. 20260912-nbutko-docs-refactor.html. Feature name is lower-case-with-dashes and is shared across a feature's PRD, wireframes, and plan so they can be found together. Date is the day the document was opened.
  • Author is a context hint, not a credit. It answers "who can tell me about this?" — usually the person who opened the doc, who has enough context to answer questions or to route to someone who does. It does not change when someone else picks the work up midstream, it need not be exactly right, and it says nothing about who did the work. Agents writing on a person's behalf use that person's handle.
  • Lifecycle: every artifact starts in wip/. When the feature is done, it is (1) updated to reflect the work actually completed, (2) moved to done/, and (3) any evergreen doc it affects is updated. Artifacts in done/ are frozen thereafter.
  • Indexes: prds/index.html, wireframes/index.html, and plans/index.html each list every artifact of that type with a short description, grouped into a wip section and a done section. The wip/ and done/ directories themselves have no index. Opening or closing an artifact means updating its index.
  • Plan (required for all work): technical scope — approach, design, and the work broken into Stories, each a list of Tasks rendered as checkboxes that get checked as they complete. This is the document the existing "one story = one commit" rule operates on.
  • PRD (larger scope only): what we want to build and why — user value and experience, not implementation. Written before the plan.
  • Wireframes (anything visual): screens and flows. Written after the PRD, before the plan. Design-canvas files keep their .dc.html extension so the canvas editor still opens them.
  • Templates: one skeleton per type (PRD, wireframe page, plan with story/task checkboxes, note with head summary) lives in style/templates/. Starting a doc means copying one.
"Larger scope" and "touches visuals" are judgment calls, made at the start of a feature and recorded in the plan's header. Rule of thumb: a PRD is warranted when the work changes what the player experiences or why a system exists (a new milestone, a retune with targets, a new screen); a bug batch or a refactor with no player-visible change needs only a plan. Wireframes are warranted whenever a screen is added or its layout changes — color/copy tweaks inside an existing layout are not.

4.3 notes/: the gotcha dump

  • Any time an agent learns something non-trivial during development or debugging that another agent is likely to trip on, it leaves a note: [YYYYMMDD]-[author]-[note-name].html. The note name describes the topic and need not match any feature.
  • Every note opens with a 5–10 line "when to read this" summary, so an agent can read the head of the file and decide whether to load the rest.
  • notes/index.html lists every note with a one-sentence "relevant when…" description. Adding a note means adding its index line.
  • Stale notes get a loud warning, not silent rot. A note is not rewritten when it ages, but a later author who finds it wrong or obsolete must mark it — a banner at the top such as SOME CONTENT MAY BE OUTDATED or NO LONGER RELEVANT, dated, with a line on what was found and, if there is one, a link to the newer note — and update its index line to match. A wrong note taken as authoritative is worse than no note.
  • Notes live in the repo, not in any one agent's private memory, so every author's agents share them. Session memory is for personal preferences and workflow feedback only; project gotchas go here.

4.4 style/

The docs' shared stylesheet, the document templates, and any visual element used by more than one document (icons, shared diagrams). Nothing in style/ is project documentation in its own right.

6. The experience after

Starting a session. An agent reads CLAUDE.md, which says: evergreen docs are at the top of docs/, the active plan is under plans/index.html's wip section, gotchas are in notes/index.html. It skims the indexes (one line per entry), opens the one or two documents that match the task, and never wonders whether the roadmap is current.

Starting a feature. The agent decides — and writes down in the plan header — whether the work needs a PRD and wireframes. It copies the template from style/templates/, names the file [today]-[handle]-[feature].html under wip/, adds an index line, and breaks the work into stories with checkbox tasks. If it wants an example of a good PRD or plan, done/ is full of them. The existing "one story = one commit, check in between" rule now has an obvious artifact to tick.

Finishing a feature. The close-out checklist in the conventions doc: reconcile the plan with what shipped and tick the boxes; add the status banner; git mv the PRD, wireframes, and plan to done/ and move their index lines; update every evergreen doc the feature touched; write a note if anything surprising was learned and add its index line. The last commit of a feature is a docs commit.

Six months on. The top of docs/ has roughly the same handful of files it had when this feature closed, all true. done/ holds a dated, findable history. notes/ has grown by a file or two per feature, a couple of them wearing an "outdated" banner, and its index is the fastest way to learn what the code will not tell you.

7. Success criteria

  • Every file under docs/ is either top-level evergreen, in style/, in notes/, or in a {prds,wireframes,plans}/{wip,done}/ directory with a convention-conforming name. No stragglers.
  • A read-through of each evergreen doc finds no sentence that is false about the repo at the close of this feature, and no milestone-history narration — but each design decision still has its current "why."
  • Each of the four sub-indexes lists every artifact in its directory, and nothing that isn't there.
  • Every link in docs/, CLAUDE.md, src/, and content-pipeline/ that targets docs/… resolves; every doc renders styled when opened directly from the filesystem.
  • The conventions doc and templates alone are enough for an agent to correctly open, name, index, and close a hypothetical new feature — verified by asking a fresh session to do exactly that.
  • notes/index.html lists at least the seeded gotchas, each note's head summary stands on its own, and no repo-relevant gotcha remains only in session memory.
  • This PRD and its plan are in done/, reconciled, when the feature closes.

8. Decisions recorded while writing this PRD

Templates: yes. Four skeletons in docs/style/templates/, one per document type.
Indexes: one per artifact type, at prds/index.html level. Grouped wip / done with a short description per feature. Not inside wip/ or done/.
Author is a context hint. "Who can tell me about this," not "who did the work." Does not change midstream; exactness doesn't matter; agents use the handle of the person they work for.
The M5 audit may be split. If its "why" (findings, rationale) and any plan-shaped material separate cleanly, split them like the milestone docs; if not, it lives whole in prds/wip/ as the document the M5 plan traces every story back to. The plan makes the call.
Session memory moves to notes. Repo-relevant gotchas in the maintainer's private auto-memory become notes so other authors' agents can see them; memory keeps only personal preferences and workflow feedback. The conventions doc says so.

9. Risks

  • Link rot in the move. Sixteen documents cross-link heavily, and source comments link into docs/design/. Mitigated by R9's explicit link pass and by preferring git mv so history follows the file.
  • Over-scrubbing the evergreen docs. Cutting history can also cut the reason a rule exists. The rule is: an evergreen doc keeps every "why" that is still the current understanding, and points to the done/ record for further context. What goes is the narrative of how it changed, not the reasoning for how it is.
  • Reshaping drifts into rewriting. Splitting an old scope doc into a PRD and a plan is editorial work, and it is tempting to "improve" the content. Mitigated by the non-goal above: restate and reorganize what was recorded, keep the original's decisions and numbers, and let the status banner carry what changed afterward.
  • Convention decay. The pattern only survives if every feature closes with the checklist. Mitigated by putting the checklist in CLAUDE.md's non-negotiable working rules, next to "one story = one commit."
