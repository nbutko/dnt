Content

What he actually types, what he's fighting, and how both get generated — the 14-tier ladder, the dungeon roster, and the pipeline that fills them, as they run today.

The player's typing prompts and the monster roster are both plain data, not hardcoded in a component — adding a monster or a hundred more lines at a tier is a content change, never a code change. This document restates that data as it exists now; how it was designed is in the content-v2-tiers PRD and how the pipeline was built is in its plan. The earlier, superseded 10-tier design is content-v1.

The 14-tier ladder

Each tier adds exactly one new typing demand — new keys, more length, or one new character class. Tiers 1–9 are the character-set ramp; the ceiling is reached at T9, so tiers 10–14 add nothing new to the character set and are a pure length/stamina ramp instead (passages, not lines).

Dungeon → tier mapping

11 dungeons, 14 tiers, one habitat per dungeon. Dungeon N serves regular text tiers [N, N+1, N+2] (the encounter d20's low/mid/high band picks within that range); its boss serves N+3. This is src/config/dungeon-tiers.ts today — the source of truth code reads:

The cast and the monster roster

A standing ensemble of five voices — Mab (GM/narrator), Bront (Fighter, terse declaratives), Quill (Wizard, precise and numeric), Sable (Rogue, sly asides), Fife (Bard, florid and exclamation-heavy) — runs a hidden 5-part campaign per dungeon, seeded from that dungeon's habitat and monster roster. Different voices feed different tier bands (Bront's short declaratives are the T6 goldmine; Quill's stat blocks feed T8/T9's numbers and symbols). Full character sketches are in the PRD's §4.

The monster roster the game actually fights (src/content/monsters.json, read by src/content/monsters.ts) is a curated, hand-picked subset — not the full manual. The full candidate pool the pipeline drew each dungeon's cast from is content-pipeline/monster-manual.json: 501 monsters, each tagged with a real D&D 5e challenge rating and one or more habitats, used only at authoring time by content-pipeline/manifest-gen.ts to propose a CR-banded, habitat-matched candidate list per dungeon. It is pipeline input data, not shipped code or documentation — nothing at runtime reads it.

How the pipeline runs today

All eleven dungeons' content is generated, offline, by content-pipeline/ and shipped as static JSON — no LLM and no generator runs on the kid's Chromebook. The stages, in order, as the scripts in content-pipeline/ actually run:

  1. manifest-gen.ts — deterministic. Reads monster-manual.json and dice.json, emits generated/manifest.json: per dungeon, a CR-banded candidate roster, a dice slice, and the section→tier→mode map (drill / compose-short / compose-long) derived from the tier mapping above.
  2. Showrunner (agent, per dungeon) — writes that dungeon's 5-section campaign transcript (content-pipeline/<habitat>/campaign.md) from the manifest's brief, cast, and roster.
  3. draw.ts — deterministic. Reads a dungeon's transcript once, emits pre-drawn (seed word + line window) bundles per section and tier — the only thing the compose step below ever sees, so no compose agent reads a whole transcript.
  4. Compose (agent, one per section or per long tier) — writes fresh, tier-legal sentences or passages from a handful of seed bundles ("seed-and-compose": corpus flavor in, LLM grammar and coherence out).
  5. drill-gen.ts — deterministic, independent of the above. Generates tiers 1–4's keyboard-constrained word/phrase drills from hand-curated legal-key-set word banks; emits generated/drills/tier-01.json–tier-04.json.
  6. assemble.ts — deterministic. Folds a compose run's output cells into that dungeon's generated/pools/<habitat>.json, idempotently (a later pass or top-up replaces only the cells it covers).
  7. lint.ts — deterministic. Checks tier-legality, dedup, and per-cell coverage (target count, required character classes, letter diversity) on a dungeon's pool; emits the linted generated/pools/<habitat>.clean.json and flags any shortfall for a targeted top-up.
  8. merge.ts — deterministic. Folds each dungeon's drilled tiers (≤4) and linted prose (≥5) into one uniform generated/pools/<habitat>.merged.json — a full section×tier grid, every dungeon the same shape.
  9. ship.ts — deterministic. Reads every dungeon's .merged.json and emits the single bundled src/content/text/library.json the game imports at build time, keyed dungeon → tier → lines (sections collapse away — a regular fight at a served tier draws the union of all regular sections at that tier; the boss draws its own).

src/content/text-banks.ts loads that library at runtime: a dungeon's own lines at the exact tier if present, else every dungeon's lines at that tier, else the nearest easier tier globally — content never runs out, it degrades down. All eleven dungeons' pools exist and every tier 1–14 has content; src/content/text-banks.test.ts covers the loader.

Deterministic scripts do all the reading (corpus draws, legality/dedup/coverage checks, the T1–4 drills) at zero token cost; LLM calls are spent only on the two compose steps, and each compose call sees a tiny slice of seed bundles, never a whole transcript or the codebase. That split is why generating the whole game's content library was a roughly one-time, ~1M-token job rather than tens of millions — the full reasoning and the agent-tree shape are in the plan's §7.

Visual identity

No image assets. The game is presented as text and typography throughout — a monster description, its HP, its own live-typed line (typos and self-corrections rendered character by character), the player's prompt, and an on-screen keyboard highlighting the next few keys. Hits and misses read through color flash, a CSS shake, and damage numbers, not art. The full visual system (palette, type, layout, keyboard) is visual-spec.html; how each screen actually looks and behaves is screens.html.
