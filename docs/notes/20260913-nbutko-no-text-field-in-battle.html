The battle screen has no text field, on purpose

A hidden <input> is a focus trap with no escape and an autocorrect target for ChromeOS; keystrokes come from window keydown instead.

author: nbutko · opened: 2026-09-13
When to read this. You're about to add an <input>, <textarea>, or contentEditable to the battle screen — "for focus", "for accessibility", "so the Chromebook's on-screen keyboard pops up", or because a library expects one. Or you're debugging "typing stopped working" / "my word got changed" on the Chromebook and reaching for autoFocus, onBlur-refocus, or autocorrect="off". Don't. Read ui/hooks/useTypingInput.ts first; it is the only keystroke source, and the two bugs you'd be reintroducing were the worst the game has had.

Relevant when

You're touching anything that captures the player's typing in a battle, or considering putting a focusable text control on the battle screen.

The gotcha

Through M0–M4 the player typed into a real <input> that was visually hidden with sr-only and whose .value was the typed string. Two things made that a trap on the one device that matters:

  • Focus. The element had to hold DOM focus to receive anything, and it only got focus from autoFocus on mount. Any touchpad tap, touchscreen tap, or Tab press moved focus away; nothing moved it back; and because the element was invisible there was no box to click into. The reported symptom was "keys stop affecting the prompt mid-fight, and it never recovers until reload."
  • ChromeOS autocorrect. ChromeOS applies its own auto-correction, auto-capitalization, and spellcheck to any editable field. A bare text field got all three, so a correctly typed line was sometimes rewritten into a miss. The autocorrect/autocapitalize/spellcheck opt-out attributes have historically not been honored reliably by ChromeOS's physical-keyboard autocorrect, so they are not a fix you can trust.

Both have one root cause — an editable element in the DOM — so the fix removed the element rather than patching each symptom (the plan, with the diagnosis and decisions).

What to do

ui/hooks/useTypingInput.ts builds the typed line from window keydown while the battle is ongoing and the player isn't in a miss pause. It needs no focus (the tests deliberately type with nothing focused) and gives the OS nothing to rewrite. If you need new typing behavior, change the hook's key rules; if you need a control the player clicks, make it a <button>. If a future feature truly needs an editable field on this screen, re-read the two bullets above first and plan for both.

History

  • 2026-09-13 — written at the close of typing-input-rework, after both Chromebook reports were traced to the hidden input. The focus-loss half was confirmed fixed by the maintainer's play-test; the autocorrect half is structurally gone but awaits a word the OS used to rewrite.
