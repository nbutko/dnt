highestUnlockedTier can be 12, even though there are only 11 dungeons

The save field that tracks dungeon-tier unlocks uses "one past the last real tier" to mean "everything is cleared" — there is no tier 12.

author: nbutko · opened: 2026-07-04
When to read this. You're touching anything that reads or writes SaveData.highestUnlockedTier — tier-unlock logic, the world map's cleared/available/locked state, dungeon-tier config, or a save migration — and a value of 12 looks like an off-by-one bug. It isn't; it's the deliberate "all 11 dungeons cleared" sentinel.

Relevant when

You see or need to produce highestUnlockedTier === 12 and there is no tier 12 dungeon to match it, or you're writing a bounds check against the 11-tier ladder.

The gotcha

There are exactly 11 dungeon tiers (config/dungeon-tiers.ts, one per habitat, Grassland through Urban). A single number, highestUnlockedTier, tracks progress: tier N is considered "cleared" iff N < highestUnlockedTier. That works cleanly for tiers 1–10, but tier 11 (Urban, the finale) has no "tier 12" to unlock when its boss falls — and the map still needs to show tier 11 as cleared once the Tarrasque is dead. The fix chosen during M2 was to let highestUnlockedTier legitimately reach 12, meaning "all 11 tiers, including Urban, are cleared." cleared(N) = N < highestUnlockedTier then holds for every tier with no schema change or special-cased "is this the last tier" branch.

What to do

Don't clamp highestUnlockedTier to ≤ 11, and don't treat 12 as invalid input in validation or save-migration code — it's the correct terminal value. If you add a 12th dungeon tier some day, this sentinel scheme breaks (there'd be a real tier 12 competing with the "all cleared" meaning) and needs a deliberate redesign, not a quiet bump. The field and the rule are documented inline at its declaration in src/domain/save.ts.

History
