Documentation Conventions

How docs/ is laid out, how to name and place a new document, and how to open and close a feature's docs — without reading a PRD to learn it. Five minutes, read straight through.

1. The layout

DirectoryWhat lives there
docs/ (top level)Evergreen docs: the project as built today. No milestone narration.
style/The shared stylesheet, the document templates, any asset used by more than one doc. Not documentation itself.
prds/What we want to build and why (larger-scope work only) — index.html + wip/ + done/.
wireframes/Screens and flows (anything visual) — same index.html + wip/ + done/ shape.
plans/The technical approach and the stories/tasks — required for every piece of work. Same shape.
notes/Dated gotchas that aren't evergreen truths and aren't tied to one feature's lifecycle — index.html + flat files.

wip/ and done/ never have their own index; the type's index.html one level up is the index. An empty wip/ or done/ still exists in git (a .gitkeep) so the shape is visible even before it's used.

2. The evergreen rule

Top-level docs are present tense: they describe the repo now, not how it got here. They may — and should — carry the current "why" ("the engine never imports React because…"); what they drop is the narrative of how a design changed ("in M2 we tried a skill tree, then…" links to the done/ plan instead of staying in the text).

Every session starts cold. A stale sentence in an evergreen doc costs the next agent a wrong assumption or a code spelunk. Trust-by-location only holds if closing a feature always includes fixing the evergreen docs it touched — that's the maintenance obligation, not optional cleanup.

Maintenance obligation: a feature's last commit is a docs commit. If the work changed what an evergreen doc says, that doc gets updated in the same close-out, not "later."

3. Naming

Dated artifacts (PRD, wireframes, plan, note) are named: 

[YYYYMMDD]-[author]-[feature-or-topic].html
  • Date is the day the document was opened.
  • Author is a context hint, not a credit — "who can tell me about this?" It doesn't change when someone else picks the work up, and doesn't need to be exact. On this repo it's almost always nbutko.
  • Feature name is lower-case-with-dashes and shared across one feature's PRD, wireframes, and plan, so the three are findable together (e.g. 20260912-nbutko-docs-refactor for all three). A note's "topic" need not match any feature name — notes are gotchas, not features.

4. When a PRD or wireframes are warranted

A plan is required for every piece of work. A PRD is warranted when the work changes what the player experiences or why a system exists — a new milestone, a retune with targets, a new screen. A bug batch or refactor with no player-visible change needs only a plan. Wireframes are warranted whenever a screen is added or its layout changes; a color or copy tweak inside an existing layout is not. This is a judgment call made at the start of the feature and recorded in the plan's header status line.

5. Lifecycle

  1. Open: copy the right template (§7) into wip/ under the naming rule (§3); add a row to that type's index.
  2. Work: tick ul.tasks checkboxes as stories complete. One story, one commit.
  3. Close — see the checklist in §11.

roadmap.html lists milestones only — a feature that isn't a milestone (a bug batch, a retune, this refactor) is tracked by its plan's row in plans/index.html, nothing on the roadmap.

6. Index upkeep

Each of prds/index.html, wireframes/index.html, plans/index.html lists every file of that type, one row per file, grouped into a wip table and a done table, and every such table shares the same three columns: Opened | Document | Summary ("Opened" is the date in the filename). notes/index.html keeps one table (notes don't move), columns Date | Note | Relevant when. A file is never unlisted — opening or closing a document means adding or moving its row in the same commit.

7. Templates

One skeleton per document type lives in style/templates/: prd.html, wireframes.html, plan.html, note.html. Each carries bracketed […] prompts telling you what goes in each section, and each template's <link rel="stylesheet"> already points at its destination directory (../../style/style.css for a PRD/wireframes/plan landing in wip/, ../style/style.css for a note landing in notes/) — so it renders unstyled if you open it in place under style/templates/, and styled once copied to wip/. To start a document, copy the template into the right wip/ directory, rename it to the convention (§3), and fill in the prompts — don't write one from scratch.

8. Notes

  • Write one when an agent learns something non-trivial that another agent is likely to trip on. One gotcha per file; the topic in the filename, not a feature name.
  • Opens with a callout why titled "When to read this" — 5–10 lines an agent can read without loading the rest of the file.
  • Never silently corrected. A note found wrong or stale gets a dated banner outdated (or retired) at the top saying what changed, plus a link to the newer note if there is one — the index line updates to match. Deletion is not how a note goes stale.

Memory holds preferences only. A maintainer's session memory is for personal preferences and workflow feedback across sessions — repo knowledge (gotchas, traps, "why is this weird") lives in notes/ where every author's agents can see it, not in one person's private memory.

9. Banners

A <div class="banner VARIANT"> sits directly under the header of any dated artifact — PRD, wireframes, plan, or note. Four variants:

VariantMeans
doneThe work shipped. What landed, what didn't, where the evergreen description now lives.
wipOpen and in progress — the normal state of anything under wip/.
outdatedSome content is stale but the document isn't fully superseded; says what changed and, if one exists, links the replacement.
retiredSuperseded outright — points to what replaced it.

10. Checkboxes

Task lists use the glyphs ☐ (open) and ☑ (done) as plain text — the first character of each <li> — inside a <ul class="tasks">. Never an <input type="checkbox">: a static file can't persist its state, so a form control would silently lie.

11. Close-out checklist

Copy this into the closing commit's checklist (or just follow it):

  • ☐ Reconcile the plan: tick every task actually done; leave the rest unticked.
  • ☐ Add (or update) the banner at the top of the PRD/wireframes/plan: what shipped, what didn't, where the evergreen description now lives.
  • ☐ git mv the PRD, wireframes, and plan into their done/ directories.
  • ☐ Move each moved file's row from the wip table to the done table in its index.
  • ☐ Update every evergreen doc the feature touched so nothing it says is false.
  • ☐ Write a note (with index row) if the feature surfaced a gotcha worth not re-learning.
  • ☐ Run the link audit (the script the docs-refactor plan wrote in its §7.1 — it checks every href on disk); commit.
