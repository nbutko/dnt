localhost:5173 and 127.0.0.1:5173 are different origins

Same dev server, same port — but the browser treats them as two unrelated origins with two unrelated IndexedDB/localStorage stores.

author: nbutko · opened: 2026-07-05
When to read this. A save (or anything else in browser storage) appears to have "reset" or "vanished" between two sessions that both look like npm run dev at port 5173 — before assuming a bug in save loading/migration, check whether the two sessions actually used the same hostname in the address bar.

Relevant when

You (or an agent's browser tool) are testing the app at localhost:5173 in one sitting and 127.0.0.1:5173 in another, and the save data doesn't seem to carry over.

The gotcha

Browsers scope storage (IndexedDB, localStorage, cookies) by origin, and localhost and 127.0.0.1 — despite resolving to the same machine and the same Vite dev server — are two distinct origins. Each gets its own, completely separate IndexedDB database, so a save written under one hostname is invisible under the other. This surfaced during M2 playtesting as an apparent bug: the app went blank at localhost:5173 (see the companion note on IndexedDB opens hanging) while 127.0.0.1:5173 rendered fine in the same browser at the same time — because the two origins' IndexedDB stores are unrelated, one being wedged said nothing about the other.

What to do

Pick one hostname for a given testing session and stick with it — don't hop between localhost:5173 and 127.0.0.1:5173 expecting shared state. If a save looks like it reset, check the address bar's hostname before suspecting domain/save.ts's migration logic. This also matters for the agent browser tools, which default to one hostname — confirm which one before concluding a save bug is real.
