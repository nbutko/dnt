Deleting the save DB from DevTools can wedge the whole origin

Deleting an IndexedDB database from DevTools while any tab still holds an open connection to it can leave that origin's IndexedDB answering nothing, forever — a debugging action, not a code bug.

author: nbutko · opened: 2026-07-04
When to read this. You (or an agent driving a browser tool) want to reset save state during testing by deleting the IndexedDB database from DevTools' Application panel or console, or you're staring at an app that went permanently blank at one origin right after doing that.

Relevant when

You're trying to wipe a save for testing and a tab that has (or recently had) the app open at that origin is still around.

The gotcha

indexedDB.deleteDatabase() — whether triggered from DevTools' delete button or the console — blocks until every open connection to that database closes. If a tab holding an open SaveProvider connection is left around (even backgrounded, even a different tab than the one you're deleting from), the delete request can sit pending forever, and the origin's IndexedDB store then answers no further open() calls either. The symptom is identical to the companion note's (IndexedDB's open() can hang forever) — a blank page, no console error — but the cause here is a debugging action, not app code. Confirmed with fake-indexeddb unit tests and by opening a fresh database name in the same tab: the app's own code was not at fault.

What to do

Close (or fully reload) every tab open at that origin before deleting its save database from DevTools. If a hang happens anyway, switching origin (127.0.0.1:5173 vs localhost:5173 — see the separate-origins note) is a faster way to get a clean slate than debugging the reducer/storage code. Prefer hardResetSave() (src/domain/save.ts) or the app's own UI for wiping a save where possible, rather than deleting the database out from under a live connection.
