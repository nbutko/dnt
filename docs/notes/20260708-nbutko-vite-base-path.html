/dnt/ is a production-build-only base path

npm run dev always serves from root; only the built site (deployed on every push to main) is served from the /dnt/ subpath.

author: nbutko · opened: 2026-07-08 · relates to: M4 ship-it plan
When to read this. You're adding an absolute asset path or a link that assumes a particular base path, debugging a 404 that only happens on the deployed site (never in npm run dev), or wiring up something new in .github/workflows/deploy.yml.

Relevant when

You're touching vite.config.ts's base, adding an absolute-path asset reference, or debugging something that 404s only on nbutko.github.io/dnt/ and not locally.

The gotcha

vite.config.ts (confirmed current) sets base: command === 'build' ? '/dnt/' : '/' — the /dnt/ project-pages subpath only applies to the production build, matching https://nbutko.github.io/dnt/. Dev (npm run dev) always serves from root at 127.0.0.1:5173/, which is also how it keeps serving /docs/... for agent browser tools (see the companion note on file:// URLs). An absolute path hardcoded as /something in app code works in dev but 404s in production because the real path is /dnt/something — always go through Vite's asset handling (import, or %BASE_URL% in index.html, as the manifest link and favicon already do) rather than a literal absolute path.

Deploy itself (.github/workflows/deploy.yml) runs on every push to main (plus manual workflow_dispatch): npm ci && npm run build, then actions/upload-pages-artifact + actions/deploy-pages publish dist/ to GitHub Pages. Concurrency is capped at one deploy at a time (a newer push cancels an in-flight one).

What to do

Reference assets the way index.html already does (Vite-resolved imports, or %BASE_URL%), never a literal leading /. If something works locally but 404s on the live site, check whether it's an absolute path that skipped Vite's base-path substitution before suspecting the deploy workflow itself.
